# snipaste-hdr-fix

Fix the washed-out / dull-looking screenshots that **Snipaste** produces on HDR displays.

> 中文说明 → [README.zh-CN.md](README.zh-CN.md)

---

## The problem

With Windows HDR enabled, Snipaste 2.11.x gives you the wrong colors **either way**:

| Setting | What you get |
|---|---|
| *"Adjust colors for screenshots taken on HDR monitors"* **on** | Highlights are progressively crushed — everything looks **dull / washed-out grey** |
| the same option **off** | Everything is lifted — bright areas blow out and dark areas turn milky **white** |

Measured on a 4K QD-MiniLED display at 175% scaling, comparing a screenshot against what
is actually on screen (relative luminance percentiles):

| Percentile | On-screen truth | Option ON (bug) | Option OFF (bug) | After this fix |
|---|---|---|---|---|
| p90 | 228 | **213 (−15)** | 254 (+26) | 228 ✓ |
| p99 | 245 | **220 (−25)** | 254 (+9) | 245 ✓ |
| brightest | 254 | **224 (−30)** | 254 | 254 ✓ |

See `docs/comparison.png` for the visual comparison.

## Root cause

Snipaste v2.11+ embeds the HDR tone-mapping shader from
[GEEKiDoS/bitblt-hdr](https://github.com/GEEKiDoS/bitblt-hdr).
In `tonemapper.hlsl`, SDR content is normalized so that the **SDR white point equals 1.0**:

```hlsl
float3 input_color = clamp(src_color, 0, 10000) / (white_level / 80);  // SDR white → 1.0
```

…but the knee of `linear_tonemap()` sits at **0.8**:

```hlsl
float3 linear_tonemap(float3 x)
{
    const float z = 0.8;
    const float d = 2.5;
    return lerp(x, (x - z) / d + z, step(z, x));
}
```

So pure white (1.0) is mapped to `0.8 + (1.0 − 0.8) / 2.5 = **0.88**`, i.e. **224 instead of 255** —
and every highlight above ~214 is compressed. Line 112 has the same problem
(`step(0.8, linear_luma)`), which desaturates SDR colors above 0.8.

## The fix

Two constants — the knee is moved to the SDR white point:

```diff
-    const float z = 0.8;
+    const float z = 1.0;
...
-        linear_color = lerp(linear_result, neutral_color * linear_luma, step(0.8, linear_luma));
+        linear_color = lerp(linear_result, neutral_color * linear_luma, step(1.0, linear_luma));
```

SDR content (≤ 1.0) then passes through **unchanged**, and only content brighter than SDR white
is compressed by the existing neutral tone-mapper.

**Why not just patch the bytes?** The DXBC container carries a 16-byte proprietary compiler hash.
Edit any byte and D3D11 rejects the shader (`hr=0x80070057`), upon which Snipaste marks the feature
as unsupported and **greys out the option**. The fix therefore *recompiles* the shader, so the hash
is regenerated by the compiler itself.

## Requirements

- Windows x64
- Snipaste **2.11.x** desktop build (the version that has the built-in HDR correction)
- Python 3.8+
- **No C++ compiler needed** — the tool compiles the shader with the `d3dcompiler_47.dll`
  that ships next to `Snipaste.exe`

## Usage

Put `snipaste_hdr_fix.py` and `tonemapper.hlsl` anywhere (they may live inside the Snipaste folder),
then:

```bash
python snipaste_hdr_fix.py check                 # report current state, changes nothing
python snipaste_hdr_fix.py patch                 # backup → compile → replace → verify
python snipaste_hdr_fix.py restore               # roll back to the backup

# if the script is not next to Snipaste.exe:
python snipaste_hdr_fix.py check --dir "D:\Snipaste"
```

**Then fully exit and restart Snipaste** — the shader is loaded at startup.

Notes:

- A backup (`Snipaste.exe.unpatched.bak`) is created automatically before the first patch.
- The tool verifies the new shader with D3D11 before and after writing; it refuses to write
  anything that D3D11 rejects.
- If Snipaste is running, the tool renames the exe out of the way instead of failing.

## Caveats (please read)

- **Unofficial.** Not affiliated with Snipaste or bitblt-hdr. It edits a third-party binary on your
  own machine; use at your own risk.
- **Trade-off, on purpose.** For content brighter than SDR white (HDR games/videos), the compression
  now starts at SDR white instead of at 1.3×. That headroom cannot be kept *and* have SDR white be
  255 in an 8-bit SDR output — the two are mutually exclusive, so this tool chooses SDR fidelity.
  For normal screenshots (web pages, UI, photos) nothing is lost.
- **Snipaste updates overwrite the exe.** Re-run `patch` after every upgrade.
- Do not use this with multi-GPU display setups where the monitors are driven by different GPUs —
  the upstream library does not support that either.
